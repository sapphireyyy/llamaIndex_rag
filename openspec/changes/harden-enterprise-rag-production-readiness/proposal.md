## Why

现有平台已经具备企业 RAG 的主要接口和组件，但运行时仍存在“声明为异步、实际同步执行”“声明支持流式、实际完整生成后分片”等语义缺口，租户隔离也缺少非特权 PostgreSQL 账号下的强制验收。这些差距会直接影响生产环境的响应时延、横向扩展、权限隔离和配置可追溯性，因此需要一次按风险排序的生产就绪加固。

## What Changes

- **P0：闭合异步入库链路。** 上传 API 只完成校验、持久化与可靠投递后返回 `202 Accepted`；Outbox、队列与 Worker 承担解析、切分、Embedding、索引暂存和发布，且保持幂等、重试、取消、背压与最后有效版本语义。
- **P0：把 RLS 隔离变成发布门禁。** 分离迁移账号与应用运行账号；生产运行账号不得拥有 `SUPERUSER`、`BYPASSRLS` 或业务表所有权，并必须通过真实 PostgreSQL 的跨租户读写隔离测试。
- **P1：提供能力可验证的真实流式回答。** 支持流式的模型 Provider 必须把上游增量直接传递到 SSE，保留取消、错误、引用和唯一终态语义；不支持流式的 Provider 必须显式声明并采用可观察的非流式降级，而不是伪装成 Token 流。
- **P1：明确生产模型配置。** `extractive` 保留为本地开发、测试和离线回退能力；生产配置必须显式选择并验证生成式 Provider、Secret Binding 和能力契约。**BREAKING**：依赖隐式 `extractive` 默认值启动生产环境的部署将不再被视为生产就绪。
- **P1：将文档切分参数纳入租户不可变配置。** `chunk_size`、`chunk_overlap` 需要校验、版本化并快照到入库任务；配置变化通过明确的重建索引流程生效，不修改已发布版本的解释语义。
- **P1：增加受策略约束的 OCR 处理。** 对扫描型 PDF 和无可提取文本的页面提供可选 OCR，保存页码、区域、置信度、Provider 和原文溯源；外部 OCR 仍受租户外联、Secret、配额和内容捕获策略约束。
- **P1：闭合检索策略映射。** 查询执行使用已激活助手版本引用的完整检索策略，覆盖召回、融合、重排、证据选择、阈值与预算；运行时不得用未版本化的代码默认值静默覆盖策略。
- **保持事实源边界。** PostgreSQL 继续作为租户、权限、文档状态、活动版本和配置版本的事实源；Milvus 与 OpenSearch 只作为可重建的检索投影，不得独立决定授权或发布状态。
- 本 change 不引入垂直业务流程、不替换 PostgreSQL、不要求开发/测试环境强制接入外部模型或 OCR，也不扩展到通用多模态问答。

## Capabilities

### New Capabilities

- `enterprise-rag-production-readiness`: 规定企业 RAG 在异步入库、RLS 隔离、模型流式、生产 Provider、租户级切分、OCR、策略执行和事实源一致性方面的生产就绪行为与验收标准。

### Modified Capabilities

- None. 当前主规范目录尚未包含上述运行时能力；本 change 以独立的生产就绪能力约束现有子系统，避免与尚未归档的早期 change 重复声明同名 capability。

## Impact

- 影响上传 API 的执行边界和时序、Outbox/队列协议、Worker 生命周期、任务状态与重试/取消路径，但保留现有 `202` 提交接口的外部语义。
- 影响 PostgreSQL 角色与部署配置、迁移流程、Compose/生产清单、RLS 集成测试和发布证据。
- 影响模型 Provider 与 SSE 协议实现、查询取消、能力声明、生产启动校验和 Secret Binding。
- 影响租户配置模型、助手/检索策略快照、入库重建流程、解析器/OCR 适配器、审计、用量与可观测性。
- 需要针对重复投递、Worker 重启、索引发布失败、跨租户访问、流式中断、配置切换、OCR 失败和外部索引陈旧状态增加自动化与生产化验收。
